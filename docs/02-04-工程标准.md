# 工程标准

> 极度严谨的代码质量、严格的规模控制以及绝对的安全标准。

## 1. 代码规模控制 (Scale Control)

为了保持系统的可维护性和低认知负担，本项目强制执行以下规模指标：

核心原则：单一职责 — 一个函数/文件只做一件事。
如果需要用"和"来描述它做什么，就应该拆分。

警示指标（触发时优先考虑拆分，非硬上限）：
- 函数 >50 行 或 圈复杂度 >10
- 文件 >300 行
- 参数 >6 个（React Props 除外，Props 过多时优先拆子组件）

硬上限（MUST 重构）：
- 逻辑嵌套 >4 层（JSX 结构嵌套不计）
- 函数 >80 行

## 2. 编码规范 (Coding Standards)

### 2.1 风格工具

- **Biome**: 替代 ESLint + Prettier，负责 Lint、格式化及 Import 排序。
- **强制要求**: 提交代码前必须通过 `pnpm lint:fix`。
- **Git Hooks**: 仓库保留了 `.husky/` 目录结构，但当前未提交项目级 hook 脚本；不要假设提交时会自动执行检查，提交前需手动运行验证命令。

### 2.2 TypeScript 严格模式

`tsconfig.json` 启用了 `"strict": true`，强制进行以下检查：严格空值检查（`strictNullChecks`）、严格函数类型、不允许隐式 `any` 等。所有代码必须在严格模式下通过类型检查。

### 2.3 环境变量管理

使用 [`@t3-oss/env-nextjs`](https://env.t3.gg) 进行运行时校验：

- 所有环境变量统一定义在 `src/env.ts`，包含 `server` 端和 `client` 端两个分区。
- 应用启动时自动校验环境变量的存在性和类型，缺失或类型错误时直接报错退出，防止配置错误静默导致运行时异常。
- **禁止**在代码中直接使用 `process.env.XXX`，必须从 `src/env.ts` 导入 `env` 对象。

### 2.4 核心准则

- **单一职责**: 每个模块/函数仅做一件事情。
- **DRY 原则**: 严禁硬编码（魔法数字/字符串），重复逻辑必须提取。
- **卫语句优先**: 逻辑分支应优先处理错误/边界情况，减少 `else` 嵌套。
- **自解释命名**: 变量名应描述其实际业务含义，减少不必要的背景注释。

## 3. Git 提交约定 (Commit Convention)

遵循 **Conventional Commits** 规范：

- `feat`: 新功能 (feature)
- `fix`: 修补 bug
- `docs`: 文档 (documentation)
- `style`: 格式 (不影响代码运行的变动，例如空格、分号等)
- `refactor`: 重构 (即不是新增功能，也不是修改 bug 的代码变动)
- `test`: 增加测试
- `chore`: 构建过程或辅助工具的变动 (例如，更新依赖、修改构建脚本)
- `perf`: 性能优化
- `revert`: 回滚之前的 commit
- `build`: 影响构建系统或外部依赖项的更改（示例范围：gulp、broccoli、npm）
- `ci`: 对 CI 配置文件和脚本的更改（示例范围：Travis、Circle、BrowserStack、SauceLabs）
