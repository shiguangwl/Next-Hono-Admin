# 可观测性

> 系统的透明度是排查生产问题的关键。

## 1. 结构化日志 (Logging)

使用 **Pino** 进行日志记录，特点是 JSON 格式、高性能且易于被 ELK/HyperDX 消费。

- **全局访问**: 统一从 `@/lib/logging` 导入 logger。
- **自动附带**: 日志会通过 AsyncLocalStorage 自动注入 `requestId` 上下文信息。
- **安全脱敏**: `redact` 配置自动将 `password`、`token`、`secret`、`apiKey`、`authorization`、`cookie` 等敏感字段替换为 `[REDACTED]`，防止泄漏到日志。
- **error→err 规范化**: `normalizeMeta` 函数自动将 `{ error: Error }` 转换为 `{ err: Error }`，符合 pino 序列化惯例。
- **OTel trace 注入**: logger 的 `mixin` 配置会自动将当前 OTel span 的 `traceId` 和 `spanId` 注入每条日志，实现日志与链路追踪关联。

### 1.1 模块级 Child Logger（可选）

`logger` 对象暴露了 `child()` 方法，可在需要模块标识时创建子 logger：

```ts
// 可选用法：在文件顶部创建模块级 logger
import { logger } from '@/lib/logging'
const log = logger.child({ module: 'auth-service' })

log.info('Login succeeded', { userId: 1 })
// 输出: { "module": "auth-service", "requestId": "xxx", "msg": "Login succeeded", ... }
```

项目内大多数模块直接使用全局 `logger`，仅在需要按模块过滤日志时才建议使用 child logger，不做强制要求。

### 1.2 日志 Base 字段

Logger 的 `base` 配置包含以下字段：

| 字段 | 来源 | 用途 |
|---|---|---|
| `pid` | `process.pid` | 进程标识 |
| `hostname` | `HOSTNAME` 环境变量 | 容器/主机标识 |
| `service` | 固定字符串 `'admin-scaffold-rbac'` | 服务名，多服务场景下区分日志来源 |
| `env` | `process.env.NODE_ENV` | 运行环境（development/production/test） |

```ts
// logger.ts 中的 base 配置
base: {
  pid: process.pid,
  hostname: process.env.HOSTNAME || 'localhost',
  service: 'admin-scaffold-rbac',
  env: process.env.NODE_ENV ?? 'development',
}
```

## 2. 链路追踪 (Tracing)

- **RequestId**: 每个进入系统的请求都会在 `requestContextMiddleware` 中生成唯一的 UUID（优先读取请求头 `x-request-id`，否则生成新 ID）。
- **传递**: 该 ID 会通过 `AsyncLocalStorage` 在整个调用链中自动传递，并响应在 HTTP Header 的 `X-Request-Id` 中。
- **OTel traceId/spanId**: 启用 OTel 时，`traceId` 和 `spanId` 通过 logger `mixin` 自动注入每条日志，无需手动传递。

## 3. 审计日志 (Audit Log)

- **用途**: 记录高价值业务操作（如修改权限、删除用户）。
- **用法**: 在 Hono 路由上装饰 `auditLog` 中间件，日志会持久化到 `sys_operation_log` 表。

## 4. OpenTelemetry 集成

项目在 `src/lib/telemetry.ts` 中实现了完整的 OTel SDK 初始化，涵盖 **trace、metrics、logs** 三个信号。

### 4.1 按需启用机制

OTel SDK **仅在设置了 `OTEL_EXPORTER_OTLP_ENDPOINT` 环境变量时才会启动**，未设置时完全不加载 SDK，零运行开销；相关变量由 `src/env.ts` 统一校验：

```bash
# 启用 OTel（推送至任意兼容 OTLP 的后端，如 HyperDX、Jaeger、Grafana Tempo）
OTEL_EXPORTER_OTLP_ENDPOINT=http://your-collector:4318
OTEL_SERVICE_NAME=next-hono-admin   # 可选，默认值 next-hono-admin
```

### 4.2 相关环境变量

| 变量名 | 说明 | 默认值 |
|---|---|---|
| `LOG_LEVEL` | 日志级别（fatal/error/warn/info/debug/trace/silent） | 开发 debug，生产 info |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | OTel OTLP 导出端点；**未设置时不启动 OTel** | 无 |
| `OTEL_SERVICE_NAME` | OTel 服务名标识 | `next-hono-admin` |

### 4.3 兼容的可观测平台

应用通过 OTLP 协议推送数据，兼容所有支持 OTLP 的后端：

- **HyperDX**: 支持全链路时序分析（如需本地运行，需手动创建 `docker-compose.hyperdx.yml`）
- **Grafana Stack**: Tempo（Trace）+ Loki（Logs）+ Mimir（Metrics）
- **Jaeger / Zipkin**: 链路追踪
- **OpenTelemetry Collector**: 统一收集后转发
