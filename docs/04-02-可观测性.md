# 可观测性

> 系统的透明度是排查生产问题的关键。

## 1. 结构化日志 (Logging)

使用 **Pino** 进行日志记录，特点是 JSON 格式、高性能且易于被 ELK/HyperDX 消费。

- **全局访问**: 统一从 `@/lib/logging` 导入 logger。
- **自动附带**: 日志会自动附加 `requestId`、`sessionId` 等上下文信息。

### 1.1 模块级 Child Logger 规范

各 service / 中间件 **必须** 使用 `logger.child()` 创建模块级日志实例，禁止直接使用全局 `logger`。
模块标识会注入每条日志，便于在 ELK/HyperDX 中按模块过滤和聚合。

```ts
// ✅ 正确用法：在文件顶部创建模块级 logger
import { logger } from '@/lib/logging'
const log = logger.child({ module: 'auth-service' })

log.info('Login succeeded', { userId: 1 })
// 输出: { "module": "auth-service", "requestId": "xxx", "msg": "Login succeeded", ... }

// ❌ 错误用法：直接使用全局 logger（丢失模块上下文）
logger.info('Login succeeded', { userId: 1 })
```

**命名约定**: `module` 值使用 kebab-case，与文件名对齐（如 `auth.service.ts` → `auth-service`）。

### 1.2 日志 Base 字段规范

Logger 的 `base` 配置 **必须** 包含部署元数据，以支持多实例、多环境场景下的日志定位：

| 字段 | 来源 | 用途 |
|---|---|---|
| `pid` | `process.pid` | 进程标识 |
| `hostname` | `HOSTNAME` 环境变量 | 容器/主机标识 |
| `service` | 硬编码或 `OTEL_SERVICE_NAME` | 服务名（微服务场景区分来源） |
| `version` | `APP_VERSION` 环境变量 | 版本追踪，定位回归问题 |
| `env` | `NODE_ENV` | 按环境过滤日志 |

```ts
// logger.ts 中的 base 配置
base: {
  pid: process.pid,
  hostname: process.env.HOSTNAME || 'localhost',
  service: process.env.OTEL_SERVICE_NAME || 'next-hono-admin',
  version: process.env.APP_VERSION || 'unknown',
  env: process.env.NODE_ENV || 'development',
}
```

## 2. 链路追踪 (Tracing)

- **RequestId**: 每个进入系统的请求都会在 `requestContextMiddleware` 中生成唯一的 UUID。
- **传递**: 该 ID 会通过 `AsyncLocalStorage` 在整个调用链中自动传递，并响应在 HTTP Header 的 `X-Request-Id` 中。

## 3. 审计日志 (Audit Log)

- **用途**: 记录高价值业务操作（如修改权限、删除用户）。
- **用法**: 在 Hono 路由上装饰 `auditLog` 中间件，日志会持久化到 `sys_operation_log` 表。

## 4. 可观测平台集成

项目内置了 **HyperDX (OTel)** 的全量配置：

- **配置文件**: `docker-compose.hyperdx.yml`。
- **查看指标**: 应用通过 OTLP 协议将日志、链路数据推送至 HyperDX，支持全链路时序分析。
