# 部署与运维

## Docker 部署（推荐）

### 镜像构建

项目使用**多阶段构建**，产物为 Next.js standalone 模式。

```dockerfile
# 构建阶段
FROM node:22-alpine AS base     # 基础镜像
FROM base AS deps               # 安装依赖
FROM base AS builder            # 构建 Next.js (standalone)
FROM base AS runner             # 生产运行时
```

```bash
# 构建
docker build -t next-hono-admin .

# 运行
docker run -d \
  -p 3000:3000 \
  -e DATABASE_URL="mysql://user:pass@host:3306/next_hono_admin" \
  -e SESSION_COOKIE_NAME="auth_session" \
  -e SESSION_TTL_DAYS="7" \
  -e AUTO_DB_MIGRATE=true \
  -e AUTO_DB_SEED=false \
  next-hono-admin
```

### Docker Compose

实际 `docker-compose.yml` 使用**预构建镜像**部署，通过环境变量指定镜像名称和标签，不在 Compose 内构建：

```yaml
# docker-compose.yml
services:
  app:
    image: ${IMAGE_NAME:-next_hono_admin_service}:${IMAGE_TAG:-latest}
    container_name: ${CONTAINER_NAME:-app}
    ports:
      - "${APP_PORT:-3000}:3000"
    env_file:
      - .env.production      # 生产环境配置文件
    environment:
      - TZ=Asia/Shanghai
    restart: always
    healthcheck:
      test: ["CMD", "wget", "--no-verbose", "--tries=1", "--spider", "http://localhost:3000/api/health"]
      interval: 30s
      timeout: 10s
      retries: 3
      start_period: 40s
    logging:
      driver: json-file
      options:
        max-size: "10m"
        max-file: "3"
```

```bash
IMAGE_NAME=next-hono-admin IMAGE_TAG=latest docker compose up -d
```

> **健康检查**: Compose 配置了 `/api/health` 端点的健康检查，容器启动 40 秒后开始探测，失败 3 次则标记为 unhealthy。

## 手动部署

```bash
# 构建
pnpm build

# 启动（standalone 模式）
cd .next/standalone
node server.js

# 或使用 pnpm
pnpm start
```

**注意事项：**

- 需要将 `public/` 和 `.next/static/` 复制到 standalone 目录中
- standalone 模式自动包含运行时依赖，无需 `node_modules`
- 确保生产环境变量已正确配置

## 数据库运维

```bash
# 开发环境：直接同步 Schema
pnpm db:push

# 生产环境：生成 → 审查 → 执行
pnpm db:generate
git diff drizzle/                 # 审查生成的 SQL
pnpm db:migrate

# 查看数据
pnpm db:studio                    # Drizzle Studio (localhost:4983)

# 重新生成种子数据
pnpm db:seed
```

### 自动迁移机制

当 `AUTO_DB_MIGRATE=true` 时，Next.js 启动后通过 `src/instrumentation.ts` 执行：

```ts
// src/instrumentation.ts → register()
await ensureDatabaseInitialized()
  → verifyConnection()   // 连接验证（最多重试 3 次，每次间隔 2s）
  → runInitSteps()
      → runMigration()   // 执行 drizzle/ 目录下的迁移文件（AUTO_DB_MIGRATE=true）
      → runSeed()        // 执行种子数据（AUTO_DB_SEED=true）
```

## 日志

### 开发环境

使用 `pino-pretty` 格式化输出：

```bash
pnpm dev
# 通过 pino-pretty 输出单行日志，保留北京时间时间戳
```

### 生产环境

输出 JSON 格式日志，可对接 ELK/Loki 等：

```json
{
  "level": "info",
  "time": "2026-04-07T10:20:30.123+08:00",
  "service": "admin-scaffold-rbac",
  "env": "production",
  "requestId": "abc-123",
  "msg": "GET /api/admins?page=1 [admin#1] → 200 15ms"
}
```

### 审计日志

写操作（创建/更新/删除）自动记录到 `sys_operation_log` 表，包含：

- 操作模块、操作类型、操作描述
- 请求方法、URL、请求参数
- 操作人、IP 地址
- IP 归属地（`ipLocation`，数据库存储字段，审计中间件不自动填充）
- 响应结果（`responseResult`，数据库存储字段，审计中间件不自动填充）
- 执行耗时、执行状态

## 监控集成

项目在 `src/lib/errors/monitor.ts` 中定义了 `ErrorMonitor` 接口，可通过 `addErrorMonitor()` 注册自定义监控实现。Sentry 集成作为使用示例已在文件注释中提供：

```ts
// src/lib/errors/monitor.ts（示例代码，按需启用）
import * as Sentry from '@sentry/node'
import { addErrorMonitor } from '@/lib/errors'

class SentryMonitor implements ErrorMonitor {
  captureError(error: Error, context?: Record<string, unknown>): void {
    Sentry.captureException(error, { extra: context })
  }
}

Sentry.init({ dsn: env.SENTRY_DSN })
addErrorMonitor(new SentryMonitor())
```

## 部署脚本

`scripts/deploy.sh` 提供了完整的远程部署自动化流程：

- **工作流**: 本地构建镜像 → SSH 传输到远程服务器 → Docker Compose 部署
- **回滚**: `--rollback` 参数可一键回滚到上一次成功的部署版本
- **预演模式**: `--dry-run` 参数模拟所有步骤但不实际执行
- **配置文件**: 默认读取 `scripts/.deploy.env`；仓库当前未提供 `.deploy.env.example`，需按 `deploy.sh` 中校验项手动创建或通过 `--config` 指定

```bash
# 正式部署
./scripts/deploy.sh

# 预演（不实际执行）
./scripts/deploy.sh --dry-run

# 回滚到上一版本
./scripts/deploy.sh --rollback

# 使用指定配置文件
./scripts/deploy.sh --config scripts/.deploy.prod.env
```

## Session 清理任务

`instrumentation.ts` 在应用启动时调用 `startSessionCleanupTask()`，启动后台定时任务清理过期 Session：

- **初始延迟**: 启动 30 秒后执行第一次清理
- **清理周期**: 每 1 小时清理一次
- **清理逻辑**: 删除 `sys_admin_session` 表中已过期或已撤销的 session 记录
- **幂等保护**: 同一 Node.js 进程内重复触发 `startSessionCleanupTask()` 时会跳过重复注册，避免开发态或重复初始化产生多组定时器
